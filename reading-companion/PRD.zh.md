# Reading Companion —— 产品需求文档（PRD）

*状态：草稿 · 负责人：ZHENXIANG · 最近更新：2026-06-25*

---

## 1. 问题与愿景

在非母语或专业领域阅读时，读者会不断遇到看不懂的词或短语。当前的流程是：复制词 → 切到词典或翻译 → 在多个义项中挑选 → 切回原文——这会打断阅读。

**Reading Companion：** 选中任意词或短语 → 由你选择的大模型，用你的母语给出它**在这篇文章语境中的含义**。一键即可保存到 Obsidian 或本地 `.md` 文件。

刻意不做词典式兜底：价值在于**当前语境下适用的那个含义**，而不是让你从一堆义项里自己筛。

### 1.1 目标场景

从两个维度来界定「词/短语帮助」的需求。两类阅读对象的差别不只在主题，更在于**「帮助」意味着什么**：

| 阅读对象 | 读者需要的 | 侧重 |
|---|---|---|
| **专业/学术**（法律、工程、计算机等） | 语境中的**解释** | 准确性 + 理解该术语所**指代**的过程、结构或机制——而非仅给同义词 |
| **外文文学** | 语境中的**翻译** | 此处的文学性、语境化含义——它在「这里」读起来是什么意思 |

按**平台**划分，需求又分为离线 PDF 阅读器与在线网页阅读。

**v1 聚焦：**
- **平台：** 在线**网页阅读**（离线 PDF 阅读器不在范围内）。
- **阅读对象：** 外文**文学**，以及**以休闲方式阅读的专业内容**——是带着好奇深化理解的读者，而非据此采取行动的从业者。

### 1.2 定位与非目标
- **休闲/学习场景，而非高问责场景。** 它**不**用于关乎生命或权利的关键解读——例如**药品说明书**上一旦理解错误就危及健康的用量术语，或某个案件中**对某个词的法律解释**。这些需要权威、可追责的来源，而本工具刻意不以此自居。

## 2. 两种产品形态（相同的阅读体验，两条保存路径）

**阅读/释义体验始终由浏览器插件承担。** 只有浏览器插件才能在实时网页上画出「点词即释」的界面。安装进 Obsidian 的代码只能运行在 Obsidian 窗口内，无法增强你在 Chrome 里读的网页。因此两种形态都通过插件在实时网页上阅读文章——区别只在于**保存到 Obsidian 的方式**。

| | **形态 B —— 独立插件**（v1） | **形态 A —— 插件 + 配套 Obsidian 插件**（更强的保存） |
|---|---|---|
| 阅读文章 | 浏览器插件，在实时网页上 | 浏览器插件，在实时网页上（完全相同） |
| Obsidian 侧安装 | 无 | 我们自研的小型 Obsidian 插件 |
| 长期保存方式 | `obsidian://` URI 链接，或本地 `.md` 下载 | 插件 → `http://localhost:<port>` → 由插件直接写入仓库文件 |
| 保存能力 | 单向、受限（新建/追加笔记；URL 长度限制；可能抢占焦点） | 双向、丰富（结构化 JSON、选择文件夹/模板、追加、去重、「已保存 ✓」回执） |
| 前提条件 | Obsidian 侧无需任何东西 | 保存时需运行 Obsidian 并安装我们的插件 |

**形态 A 的本地保存如何工作：** 我们的 Obsidian 插件在用户本机上开一个不接触公网的小型 Web 服务（如 `http://localhost:27123`）。插件把条目 POST 到该地址；拥有完整仓库文件权限的 Obsidian 插件随即写入 `.md` 文件并回复「已保存」。用户安装的是**我们自己**的插件，而非第三方插件。

**v1 落地目标：形态 B，仅 Chrome。** 形态 A 属于 v1 之后（见 §10）。

## 3. v1 范围

范围内：
1. 逐站点授权后再读取文章。
2. 选中词/短语 → 弹窗用用户母语给出语境化解释。
3. 保存某次查询 → 加入该文章的侧边栏列表（短期、手动、7 天过期）。
4. 侧边栏词库（Chrome 原生侧边栏）——当前文章的已保存列表。
5. 导出侧边栏列表 → 通过 `obsidian://` 存入 Obsidian，或下载本地 `.md`。
6. 设置：服务商 + API Key + 模型、母语、仓库名、保存目标。

范围外：Safari、形态 A、间隔重复复习、离线/PDF、词典兜底。

## 4. 插件文件结构

```
reading-companion/
├── manifest.json        权限、入口（MV3）
├── background.js        大模型 API 调用（service worker）
├── content.js           运行于文章页面：捕获选区、显示弹窗
├── sidepanel.html/.js   会话词库、保存按钮
├── settings.html/.js    服务商、Key、模型、语言、仓库
├── prompt-template.txt  系统提示词模板（即「agent.md」）
└── icons/
```

## 5. 数据流

```
用户选中「X」
        │
content.js：捕获 X + 完整文章正文 + URL + 标题
        │
background.js：填充提示词模板、调用大模型 → 加载动画
        ▼
弹窗：meaning_in_context → explanation
        │
写入短期记忆（浏览器存储）
        │
[ 保存 ] ──► obsidian:// URI  /  本地 .md 下载
```

- **惰性调用：** 仅在用户操作时调用大模型，绝不预翻译整篇。
- **整篇文章作为上下文：** 覆盖该词的含义及其在文章论证中的作用。
- **按「词/短语 × 文章」缓存：** 再次点选即时且免费。
- **先加载动画、后出结果：** 一次性渲染完整回复。

## 6. 释义内核

### 6.1 服务商适配层
用户自选服务商；切换是配置而非改代码。支持 Claude、OpenAI、Gemini，以及任意 OpenAI 兼容端点。API Key 仅本地存储，绝不进仓库。

### 6.2 提示词模板
占位槽：`{selection}`、`{article_text}`、`{article_title}`、`{native_language}`。

指令：用 `{native_language}` 解释 `{selection}` 在这篇文章中的用法——它的含义及与上下文的关联；短语作为整体处理，不逐字翻译。

**自动适配**阅读类型：技术术语解释其所指代的机制/过程；文学性短语给出语境化解读。兜底：若自动判别不可靠，在弹窗中提供显式的「解释/翻译」切换。

### 6.3 结构化输出

```json
{
  "selection": "…",
  "pronunciation": "…（可选）",
  "meaning_in_context": "…",
  "general_meaning": "…（可选）",
  "explanation": "1–3 句",
  "example": "…（可选）"
}
```

弹窗渲染顺序：**meaning_in_context → explanation**。文章 URL 由插件捕获，并在保存时静默附加。

## 7. 记忆

**短期（侧边栏列表）：** 由对某次查询的显式**保存**填充——不自动记录。按文章 URL 分桶存于浏览器存储，呈现在 Chrome 原生侧边栏中，每个条目自保存起 7 天后自动过期。这是用户为该文章精选的合集。每个条目包含：词/短语、释义字段、上下文片段、文章 URL、保存时间。

**长期：** 由单独的**导出**操作，把侧边栏列表归并为一篇**按文章维度的笔记**（以 URL/标题为键），存入 Obsidian（经 `obsidian://`）或本地 `.md`。（导出属于后续迭代。）

> 注：记录是手动的（保存），因此短期与长期是两个显式步骤——*先在面板中精选*，*再导出面板*——而非「自动记录 + 一次保存」。

## 8. 设置

- 服务商 + API Key + 模型
- 母语（默认取自浏览器区域设置，可更改）
- 默认保存目标（Obsidian 仓库名 / 本地下载）
- 逐站点授权（记忆）
- 每日 Token 上限（可选，v1 之后）

---

## 9. 隐私与授权

- 读取任何文章前都需逐站点授权。
- 授权文案需说明：完整文章正文 + 所选短语会被发送给用户选定的大模型服务商。
- API Key 及全部设置仅存于本地浏览器。
