# Reading Companion — 评分 Rubric

配合 `eval_set.json` 使用。**评测集**决定"测什么",**rubric**决定"每条打几分"。

## 打分总则
- 四个模块(`meaning_in_context` / `substance` / `related_terms` / `distinction`)**分开评,每个维度独立打分**,不合成总分。
- 每个维度用 **1–4 分**(偶数刻度,逼评委表态,不许选中庸的 3)。
- 评委必须同时看到 **article_text + context_sentence + selection + native_language + 待评字段**;涉及"触发恰当性"时还要看 `should_have_distinction`。
- 评委用**比生成更强的模型**、`temperature=0`,**输出结构化 JSON(分数 + 一句理由)**。
- 先跑第 1 节确定性检查(硬判),再跑第 2 节 LLM-judge(主观质量)。

---

## 1. 确定性检查(代码硬判,先跑)

任一失败先标红,再看质量分:

| 检查 | 规则 |
|---|---|
| Schema 合法 | 输出可 `JSON.parse`,字段/类型正确 |
| 语言正确 | 所有解释字段语言 = `native_language` |
| 无重复 | `related_terms[*].term` 与 `distinction.vs` 不含同一概念 |
| 触发一致 | `distinction.vs` 是否非空,应与 `should_have_distinction` 一致 |
| 锚点入文 | 若锚点声称来自文章,须确在 `article_text` 中 |
| 长度 | `meaning_in_context` 简洁(超阈值扣分);`substance` 不过长 |

## 2. LLM-judge Rubric(逐模块逐维度,1–4)

### 模块 A — `meaning_in_context`(含义简洁)
**完成度**
- 4 完整准确抓住该词在此处的意思,核心不遗漏
- 3 基本正确,略有欠缺
- 2 部分错误或明显不全
- 1 含义错误

**语境紧密度**
- 4 明显是"这句话里的用法",换语境即不成立
- 3 偏向语境,但略通用
- 2 基本是通用/词典义
- 1 与本句无关

**简洁·无门槛**
- 4 一两句、零背景可懂、不用其它术语解释术语
- 3 基本简洁,偶有小门槛
- 2 偏长,或需要背景才懂
- 1 行话套行话 / 冗长

### 模块 B — `substance`(含义/机制详解)
**理解深度**
- 4 讲清底层机制/过程/区分,读完真正"懂了"
- 3 有一定深度,但不够透
- 2 基本是把 `meaning` 换句话复述(无新增理解)
- 1 空洞或答非所问
- ⚠️ **常见词特例**:无机制可拆的普通词(tag `common-word`),`substance` 简短或留空 = 好;**硬凑长篇复述 → 此维度判 ≤2**

**语境紧密度**
- 4 机制紧扣本文的用法 / 3 偏一般但相关 / 2 脱离本文的通用讲解 / 1 跑题

**正确性**
- 4 事实准确 / 3 基本准确、小瑕 / 2 有明显错误 / 1 严重错误

### 模块 C — `related_terms`(锚定词语)
**正确性**
- 4 锚点真实、relationship 描述准确
- 3 基本正确
- 2 关系含糊或牵强
- 1 关系错误/概念虚构,**或给的是"被选中词的句法宾语/被作用对象"而非锚点**

**锚定价值**(熟悉度方向 + 帮助程度)
- 4 锚点比原词更熟悉/基础,桥接让人秒懂
- 3 有帮助但一般
- 2 锚点不比原词更熟悉,或帮助有限
- 1 用更生僻的概念"帮倒忙",或方向反了(以未知解释未知)
- ⚠️ **常见词特例**:若无更熟悉、能澄清含义的锚点,**留空 = 好**;硬凑句中其它词 → 判 1

### 模块 D — `distinction`(对比概念)
**触发恰当性**(对照 `should_have_distinction`)
- 4 应触发且命中 / 不应触发且正确留空
- 1 应触发却留空(漏) / 不应触发却硬凑(误触发)
- (此维度基本是 4 或 1;3/2 留给"触发了但对象选得勉强"的边界情形)

**正确性**
- 4 vs 概念确实易混、difference 准确
- 3 基本正确
- 2 差异说得含糊
- 1 拿了根本不会混的概念,或差异说错

**区分价值**
- 4 scenario 把两者放**同一情境**跑,边界一清二楚
- 3 有区分但不够具体
- 2 只是并列两个定义,没真正对比
- 1 没起到区分作用

## 3. Judge 输出格式(每条一个 JSON)

```json
{
  "id": "rc-009",
  "meaning_in_context": {"完成度": 4, "语境紧密度": 4, "简洁无门槛": 3, "理由": "…"},
  "substance":          {"理解深度": 4, "语境紧密度": 3, "正确性": 4, "理由": "…"},
  "related_terms":      {"正确性": 4, "锚定价值": 4, "理由": "…"},
  "distinction":        {"触发恰当性": 4, "正确性": 4, "区分价值": 4, "理由": "…"}
}
```

## 4. 聚合与判读
- 每模块取其维度均分;再按 **模块 / 维度 / 领域(domain) / tag** 分组出均分。
- 重点看几张表:`should_have_distinction=false` 组的**触发恰当性**(抓硬凑)、`jargon-prone` 组的**简洁无门槛**、`common-word` 组的 **substance 理解深度 + related_terms**(抓对常见词硬凑)。
- 每改一次 `prompt-template.txt` 就重跑,与上一版对比 → 防回归。

## 5. 评委防偏差
- rubric 里已写明"长≠好";评委与生成用**不同模型**;对生成来源 blind。
- 抽 5–8 条人工打分做校准,算与 LLM-judge 的一致性,通过后再放心批量跑。
