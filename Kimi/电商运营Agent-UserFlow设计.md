## 0. 开篇:场景 + 能力边界

### (1) 用户和场景

- **目标用户:成长期中小跨境卖家(1–5 人)**
  - **信息缺乏**:经验不足,不熟平台规则与合规红线,易违规受罚
  - **缺运营经验**:不会精细化设计大促方案、广告投流方案
  - **人力紧、时间碎**:一人身兼多职,被琐碎重复的执行占满
  - **决策快、掌控力强**:团队小、链条短,每人对全店决策权重大、能即时拍板(决策成本远低于大店铺)
  - **风险敏感**:涉及花钱(广告)与改店铺(上架/改价),操作失误代价真实且常不可逆
- **痛点**:
  - **缺运营知识**:不懂开店流程、平台规则,日常运营(选品 / 定价 / 详情 / 客服 / 广告 / 复盘)琐碎高频却无从下手
  - **规模小**:不适合「大 infra + 规模化部署 AI 中台」的重型 ToB 方案,需要轻量、即开即用的助手
- **典型场景**:开店、广告投流方案、大促方案、税务/财务等——共性是商家普遍缺信息、缺决策思路与经验。

### (2) Agent 能力边界和平台

| 级别 | 判断原则 | 典型动作(覆盖库存 → 全流程) |
|------|----------|----------|
| ✅ 全自动 | 纯内部 · 可逆 · 不对外 · 低风险 | 数据分析选品、内容生成(标题/详情/主图)、活动·券机制设计、投放方案设计、拉数据/日报 等 |
| ⚠️ 需确认(授权担责) | **对买家、平台等第三方有直接影响,或涉及商户履约/合规;后果由商户承担** | 上架/改价、改可售库存、发货/撤回发货、发布活动/发券、涉退款·投诉的客服回复 等 |
| ❌ 不做 / 转交商户 | 金额动作 + 能力外 | (金额→商户自付)Shopee Ads 充值/扣费、退款、付款/收款、充值保证金;(能力外)供应商谈判、品牌战略 |

- **Agent 载体:Kimi-Claw**
  - 部署简单,适合个人 / 小团队即开即用
  - 自带丰富 skill,满足通用任务需求
  - 可对接电商平台 API,拉取运营数据(支撑现状对齐的扫描)

## 1. User Flow 总览

> **结构**:7 个顺序阶段 + 1 个横切机制(失败兜底)。兜底是执行期可随时触发的子状态(非顺序步骤),故单列。
>
> **设计原则**
> 1. **通用性**:阶段框架任务无关、适配全部运营场景;任务差异仅体现为各阶段内子步骤的分拆,不为单一任务定制。
> 2. **用户主导决策**:关键界面状态(尤其规划展示)以**提供选项、辅助决策**为主,不替商家拍板,决策权始终归商家。

```
                    用户一句话模糊目标
                          │
                          ▼
                ┌──────────────────┐
                │ ① 意图捕获        │ 拆槽位(任务/对象/时间/隐含目标) + 判定任务类型
                └────────┬─────────┘   ▶ 任务类型决定各阶段分拆出哪些子步骤
                         ▼
                ┌──────────────────┐
                │ ② 能力预检        │ 该任务需要的授权/集成是否就位(按任务列出依赖项)
                └────────┬─────────┘   缺 → 引导去授权 or 在方案里标灰"不可用"
                         ▼
                ┌──────────────────┐
                │ ③ 现状对齐        │ 扫描(客观现状,按任务取数) + 澄清(主观意图,须问)
                └────────┬─────────┘   ▶ 扫描结果可预填 / 削减澄清问题  ◄── 方案被否回到这
                         ▼
                ┌──────────────────┐
                │ ④ 规划展示 ★      │ 可编辑执行清单 + ⚠️标记预告确认点 + 时间预估
                └────────┬─────────┘   【确认点①】确认方向与范围
                         ▼
                ┌──────────────────┐
                │ ⑤ 执行            │ 逐步汇报,中间产出可见
                │   ├ 担责确认(上货/发货/改价…)→ 确认后 Agent 做
                │   ├ 方向性决策(给选项)
                │   └ 遇金额 → 转交商户(Agent 不经手)
                └────────┬─────────┘
                         ▼
                ┌──────────────────┐
                │ ⑥ 交付            │ 完成清单 / 执行证据 / 可复用模板 / 效果监控
                └────────┬─────────┘
                         ▼
                ┌──────────────────┐
                │ ⑦ 运行期托管      │ 监控 → 异常告警 → 回到 Agent 再决策(闭合回 ⑤ 确认点)
                └──────────────────┘

  ┌─ 横切机制(非顺序阶段,执行期可随时触发)──────────────────┐
  │ ⚠ 失败兜底:再试 / 半自动 / 跳过 / 中止 —— 降级、不中断、归还控制权 │
  └──────────────────────────────────────────────────────────┘
```

> **通用性原则**:这 7 个阶段是任务无关的通用逻辑,所有任务都套同一套;差异在于**每个阶段会按任务需求分拆成不同数量、不同粒度的子步骤**

---

## 2. 阶段 1:意图捕获(Intent Capture)

**【阶段逻辑 · 通用】**
- **用户做的**:输入一句模糊目标,或顺着开场提示选一类任务。
- **Agent 做的**:
  - 拆结构化槽位(任务类型 / 对象 / 时间 / 隐含目标)
  - 判定任务类型,决定各阶段分拆哪些子步骤(同一套阶段逻辑,不跳阶段)
- **界面状态**:
  - 开场是一条用 emoji 列出**可做任务**的引导消息(顺带暗示能力边界)
  - 鼓励充分描述需求,缺口留 ③ 澄清

---

## 3. 阶段 2:能力预检(Capability Precheck)

**【阶段逻辑 · 通用】**
- **Agent 做的**:
  - 规划前先查该任务所需授权/集成是否就位
  - 缺则提示去授权,或在方案里标灰该步(注明原因),不规划做不了的步骤
- **界面状态**:一条消息把依赖项逐项 ✓/✗ 报出来

---

## 4. 阶段 3:现状对齐(Scan + Clarify)

**【阶段逻辑 · 通用】** 把"对齐到现实"拆成互补的两半:**扫描拿客观、澄清问主观**。
- **扫描(客观 · Agent 自取)**:按任务获取历史数据。
- **澄清(主观 · 必问)**:只问"扫不到、且影响方案结构"的变量,尽量做选择题。
  两条硬规矩:
  - 每个选项附一句基于扫描数据的理由,让商家据证据判断
  - 每题留「我来定 / 自定义」,选项只引导、不设限
- **界面状态**:
  - 先报扫描结果
  - 再用 ❶❷❸ 列澄清题、每题 A/B/C/D,末尾「回字母即可」

---

## 5. 阶段 4:规划展示(Plan Preview)★ 最关键的一段

**【阶段逻辑 · 通用】**
- 把预检+扫描+澄清转成**可编辑执行清单**:
  - 开头:目标摘要 + 总耗时
  - 每步标注:动作 / ⚠️确认预告 / 预估产出
- **界面状态**:
  - 整份清单一条结构化消息(emoji 编号 + ⚠️ + 缩进),末尾给指令
  - 预估基于扫描快照,执行时刷新

> 【确认点 ①】第一次确认——确认**方向与范围**(目标、这几步要不要做、预算量级能否接受),不涉逐字细节。

---

## 6. 阶段 5:执行(Execution)+ 关键确认点

**【阶段逻辑 · 通用】**
- **进度呈现**:
  - 逐步汇报,每步发「✅ 已完成 + 产出摘要」
  - 用户随时可「暂停」
- **两类确认点**(对应 ⚠️,都是"停下拿授权、确认后 Agent 动手";可逆低风险不打断):
  - 担责确认:上货 / 发货 / 改价 / 改库存 / 发券…
  - 方向性决策:需定方向的歧义
- **界面状态**:
  - 进度连续消息流(每步 ✅/⚠️ + 摘要)
  - 需确认时停下,发带选项的消息等回复

---

## 7. 阶段 6:交付(Delivery)

**【阶段逻辑 · 通用】** 一条结构化总结,四块:**① 完成清单 / ② 执行证据 / ③ 可复用模板 / ④ 效果监控**。
- **界面状态**:
  - ━ 分隔小标题 + emoji 列四块
  - "保存模板 / 查看看板"靠关键词触发

---

## 8. 横切机制:失败兜底(Failure Handling)

> 兜底是执行期(⑤)可随时触发的子状态(非顺序阶段)。原则:**降级不中断、归还控制权、保护已完成成果**。

### 五种恢复方法

| 动作 | 行为 | 方向 |
|---|---|---|
| 再试 | 重跑该步 | — |
| 半自动 | Agent 备好材料、最后一步交人手动收尾,标"已完成(降级)",继续 | 向前 |
| 跳过 | 标跳过,继续 | 向前 |
| **撤销这步** | 按"改前快照"把目标恢复到改动前,标"已撤销 / 未执行"(仅可逆 / 半可逆步骤出现) | 向后 |
| 中止 | 停掉后续,跳到交付,保留其余已完成成果 | 全局 |

### 步骤可逆性分档(决定"撤销"是否出现)

| 档 | 判据 | 示例步骤 | 撤销 |
|---|---|---|---|
| 可逆 | 改动仅在店铺内部、未对买家最终生效、可还原 | 选品分析、商品优化、活动机制草稿、客服话术草稿 | ✅ |
| 半可逆 | 技术上能还原,但买家可能已看到 | 商品上架、改价 | ✅(撤销=下架 / 改回原价,话术标注"只能止损、不能抹除已产生的曝光") |
| 不可逆 | 花钱 / 对客承诺 / 已扣费 | Shopee Ads | ❌ |

---

## 9. 横切机制:对话呈现规范(关键界面状态)

1. **每类消息 = 一个主 emoji + 固定要素**,可扫读、不刷屏(每类消息的具体要素已在各阶段「界面状态」给出,这里只立统一规范)。
2. **每条关键消息开头带阶段位置标** `[阶段 N/7 · 阶段名]`(执行期细到 `[步骤 N/M]`,即第 N 步 / 共 M 步),让商家随时知道"走到流程哪一步"。
3. **服务三类沟通需求**:告知/透明、交代/取证、能力披露/引导。
4. **全程统一指令**:暂停 / 继续 / 改 / 中止 / 看进度 / 展开N / 去掉N。

**示例 ① · 澄清提问**(选项带证据 + 留自定义):
> [阶段 3/7 · 现状对齐] 🔍 生成方案前确认 2 件事(回字母即可,每题也能「我来定」):
> ❶ 核心目标 — A. 冲量(近30天基础好) · B. 清库存(滞销品多) · C. 我来定
> ❷ 预算 — A. 稳(够现有量) · B. 加力 · C. 我来定金额

**示例 ② · 担责确认**(停下拿授权 · 三件套):
> [步骤 4/6] ⚠️ 这步要做[影响买家/店铺的动作],需你确认 · **做什么**(可核验)· **代价/影响 + 能否撤** · 👉 确认 / 改了再批 / 拒绝
